# ADR-014: Stateless Buyer Link Validation with Audit Trail

## Context

Buyers access catalogs via signed JWT links generated by mayoristas. The validation endpoint must verify the token and return the accessible catalog IDs. Performance is critical: the validation must complete in < 150ms (p95) because it is on the buyer's critical path to browsing catalogs.

## Decision

Implement buyer link validation as a stateless JWT verification:

- The JWT is signed with the tenant's `buyer_link_secret` (HS256)
- Validation checks: signature, expiration (`exp`), tenant membership, and catalog scope
- No database lookup is performed during validation
- The `buyer_links` table exists solely as an audit trail (who generated which link, when, for which catalogs)

The `token_jti` (JWT ID) in the JWT payload is stored in the `buyer_links` table for audit purposes, but is not used during validation.

## Rationale

A stateless validation eliminates the database round-trip, keeping latency well under the 150ms budget. The audit trail table provides visibility into link generation without impacting validation performance. Revocation is not required for this bolt (links expire naturally); if revocation becomes a requirement, a token blacklist can be added later.

### Alternatives Considered

| Alternative | Pros | Cons | Why Rejected |
|-------------|------|------|--------------|
| DB lookup on every validation | Can check revocation status; always up-to-date | Adds DB latency (~50-100ms); scales poorly under load | Performance requirement (< 150ms) makes this risky |
| Redis-backed token cache | Fast lookups; supports revocation | Adds infrastructure dependency (Redis); complexity | Overkill for current requirements; can be added later |
| Database lookup with caching | Reduces DB load | Cache invalidation complexity; stale data risk | Stateless is simpler and meets requirements |
| Opaque tokens with DB lookup | Can change token format without client impact | Same latency issue as DB lookup | JWT is standard and well-supported |

## Consequences

### Positive

- Validation latency: < 50ms (crypto verification only, no I/O)
- Scales horizontally: no shared state between instances
- Simple implementation: standard JWT verification
- Audit trail maintained for compliance and debugging

### Negative

- Cannot revoke individual links before expiration (links must expire naturally)
- If `buyer_link_secret` is compromised, all links for that tenant are compromised until secret is rotated
- Token payload size limits the number of catalog IDs (JWT size constraint)

### Risks

- **Risk**: Mayorista needs to revoke a link before expiration. **Mitigation**: Future enhancement: add a token blacklist table checked during validation. For now, links have a 30-day default TTL and mayoristas can regenerate with a new secret if needed.
- **Risk**: Large catalog lists exceed JWT size limits. **Mitigation**: If catalog_ids > 100, consider using a reference ID instead of embedding all IDs in the token.
